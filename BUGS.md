# Bugs

A running log of bugs noticed while working on or with the repo. Newest last.
Workflow agents: append anything you catch here (one bullet: what, where, why). Do not fix in passing.

- [ptc confirm popup] When rejecting a cell with a reason, typing under "reject with reason" and then hitting ESC does not kick you back out to the option picker — ESC is swallowed by the text input (or otherwise unhandled), leaving no way back to the approve/reject choice except cancelling the whole popup.
  - RESOLVED: the flag and the startup gate were removed entirely (2026-09-27) — `createSandbox()` takes no settings and always returns `SubprocessSandbox`; the extension only supports unsandboxed "yolo mode" (VM-based checkpointing is planned). Env var, setting field, tests, and all doc mentions dropped.
- [subagent panel] The per-subagent elapsed-time readout jitters: instead of counting up monotonically, it flickers back and forth (e.g. 15 → 14.9 → 15.1 → 15 …) several times per second, presumably because the displayed duration is recomputed from a non-monotonic or independently-sampled clock each render frame instead of being clamped to the last value.
- [docs vs behavior: execution timeout] README ("What changed in this version") claims "a real hard execution timeout for the whole Python run", but `PTC_EXECUTION_TIMEOUT_MS` is implemented as an *idle/silence* timeout that re-arms on every frame — src/python-session-manager.ts:443-467 (the code comment itself says "it measures *silence*, not total runtime"). A cell that keeps emitting stdout/progress/subagent updates can run indefinitely past the configured timeout; only RPC-protocol-level `waitForCompletion` (src/rpc-protocol.ts:668-677) sets a one-shot wall-clock timer, and the persistent-session path never lets it fire because session-manager interrupts on its own re-armed idle timer. Observed: `PTC_EXECUTION_TIMEOUT_MS=1` still let a fast cell succeed (race), while a `time.sleep(2)` cell was immediately SIGINT-interrupted and the model spent 4+ minutes retrying.
- [policy UX: blocked tools look like missing tools] With default `PTC_ALLOW_BASH=false` / `PTC_ALLOW_MUTATIONS=false`, calling `bash(...)` inside an `exec_cell` cell raises a bare `NameError: name 'bash' is not defined` (observed experimentally; root cause: getCallableTools silently filters the tools out, src/tool-registry.ts:236-254). The model gets no policy message distinguishing "tool doesn't exist" from "tool blocked by policy — ask the user to set PTC_ALLOW_BASH/PTC_ALLOW_MUTATIONS", so it cannot self-correct or explain the failure to the user.
- [env parsing: partial garbage accepted] `parsePositiveIntEnv`/`parseClampedIntEnv` use `Number.parseInt`, so `PTC_MAX_OUTPUT_CHARS=12abc` is silently accepted as 12 (src/utils.ts:24-45); conversely `PTC_MAX_PARALLEL_TOOL_CALLS=0` (a plausible "unbounded" attempt) fails the `> 0` check and silently falls back to 8. Nonsense env values are never surfaced anywhere — settings are parsed once at extension load with no warning, so typos like `PTC_EXECUTION_TIMEOUT_MS=270_000` (underscore) silently become 270.
- [package.json files vs pi.extensions] package.json declares `pi.extensions: ["./src/index.ts"]` but the npm `files` allowlist only ships `dist`, `src/python-runtime`, `tools`, and `skills` — `src/index.ts` is not published. Git installs (`pi install git:github.com/...`) work, but a registry/packaged install would be missing the extension entry point entirely.
- [.ptc-subagents-sync.json tracked with machine-specific state] `.ptc-subagents-sync.json` is git-tracked yet contains runtime state including the absolute path `editablePath: "/home/zlare/docs/src/pi-subagents/main"` and a `syncedAt` timestamp — it will differ on every machine (spurious diffs) and assumes the author's dev checkout layout.
- [tools/README.md] Docs say "Invalid tools fail startup loading instead of being silently ignored" (tools/README.md:52), but `CustomToolManager.start()` only warns and skips invalid tools at startup — see test "CustomToolManager startup loads valid tools and warns for invalid ones" (test/custom-tool-manager.test.ts:57, warning "Skipping invalid custom tool broken.js during startup"); only the low-level `loadCustomToolsFromDir` rejects (test/custom-tool-manager.test.ts:48). The README contradicts the manager's actual warn-and-continue startup behavior.
- [sys.exit() in a cell kills the persistent kernel] `session.py:692-693` re-raises SystemExit/GeneratorExit out of `_ptc_exec_chunk`, which lands in the fatal handler (session.py:819, "session terminated during execution") and breaks the exec loop (session.py:985) — so a model calling `sys.exit()`/`quit()` inside a cell tears down the whole persistent kernel, unlike KeyboardInterrupt which keeps it interactive. IPython keeps the kernel alive on SystemExit; the docstring's "stop the chunk, keep the interpreter interactive" Ctrl-C semantics don't hold for this common hallucination path.
- [sub-k token counts mislabeled in subagent ctx readout] `subagent-panel.ts:59` formats ctx tokens below 1,000,000 as `${Math.round(n / 1000)}k`, so 500 tokens renders as "1k" and 100 tokens as "0k" (Math.round(0.5)=1 / Math.round(0.1)=0). Sub-1k agents get a wrong/misleading context figure in both the panel and the transcript notification.
- [script export silently drops comments in rewritten cells] `session.py:886` re-renders any cell containing a top-level `return` via `ast.unparse(tree)`, which discards all comments (and blank-line structure) in that cell. The `_ptc_export_script` docstring (session.py:828-833) says top-level returns "become print() calls" but never warns that the affected cell's comments are lost in the durable exported script.
- [Dead telemetry path: `firstToolPath: "direct"` unreachable] `noteDirectToolCall` (src/recovery-state.ts:64) is exported to record `firstToolPath = "direct"`, but no production code ever calls it — only tests (test/recovery-state.test.ts:84). `PtcRecoveryState.firstToolPath` can therefore only ever be `"code_execution"` or `null` in real runs, so the `PtcFirstToolPath = "code_execution" | "direct"` union's `"direct"` member and the benchmark's `BENCHMARK_OBSERVED_FIRST_PATHS` "direct" value are asserted against telemetry that production can never emit.
- [Wrong param name in model-facing output preview marker] `collapseOutputPreview` (src/utils.ts:246) tells the model to continue with `read_cell_output(cell_idx=N)`, but the tool's actual parameter is `cellIdx` (src/index.ts:392-401, camelCase; also documented as `cellIdx` in EXEC_CELL_DESCRIPTION, src/index.ts:342). A model following the hint passes an unknown `cell_idx` parameter; the embedded test (test/utils.test.ts:39) locks in the wrong name.
  - RESOLVED: marker now says `read_cell_output(cellIdx=N)` (test updated); the `read_cell_output` tool also gained an optional `kernel` parameter defaulting to the most recently used kernel.
- [parseSectionedOutput silently drops preamble] `parseSectionedOutput` (src/utils.ts:196-219) collects lines before the first column-0 section marker into `preamble` but then discards it (`void preamble`), returning only the named sections. Any text preceding the first marker would silently vanish from the rendered tool result; latent today because the host always composes marker-first output, but any legacy/partial output with a preamble loses content.
- [README overstates PTC_AUTO_RECOVER_MAX_ATTEMPTS clamp] README (Environment variables section) says "PTC_AUTO_RECOVER_MAX_ATTEMPTS=1 — bounded recovery cap; values above 1 are clamped back to 1", but src/utils.ts:84 parses it with `parseClampedIntEnv(..., 1, 0, 4)` (clamped to 0–4, not 1) and src/recovery-state.ts:74 only applies `Math.max(0, ...)`. test/recovery-state.test.ts:37 ("supports multiple automatic recovery attempts when configured") explicitly exercises maxAttempts=2, so up to 4 automatic recovery messages per request are possible despite the README.
- [settings.libraryDir is never populated] `loadSettingsFromEnv` (src/utils.ts:64-95) builds a `PtcSettings` for every documented field but never sets `libraryDir`, so `PythonSessionManager.resolveLibraryDir` (src/python-session-manager.ts:993) always sees `settings.libraryDir === undefined` and only the `PTC_LIBRARY_DIR` env fallback works. There is also no settings-file loader anywhere, so the declared `libraryDir` field on the settings contract (src/contracts/settings.ts:21) is dead and cannot be configured except via env.
- [/ptc usage string omits `stop`] The `/ptc` usage notification says `usage: /ptc <interrupt|kill> [session_id]` (src/index.ts:1369) and the command description matches (src/index.ts:1362), but the accepted-action set (src/index.ts:1367) and the handler (src/index.ts:1385) also accept `stop` as a synonym for `interrupt` — the advertised usage under-reports the command's own grammar.
- [README misstates grep()'s Python return type] README.md ("Available Python functions", ~line 103) documents `grep(...) -> list[dict]`, but the tool bridge returns a `GrepResult` dict, not a list: `normalizeToolResult` builds `{ value: { matches, matchLimitReached } }` (src/tool-adapters.ts:170-181) and the generated Python wrapper types it as `class GrepResult(TypedDict): matches: List[GrepMatch]; matchLimitReached: Optional[int]` (src/tools/tool-wrapper.ts:28-31). Model code following the README would iterate the dict as if it were a list of matches and fail.
- [README eval example prompt drifts from the seeded case file] README.md:430-435 presents a "stable JSON file" example for `recovery-missing-await` with the prompt "Use Python to read package.json and return compact JSON only.", but the actual seeded file `.pi/evals/ptc/cases/recovery-missing-await.json` has the prompt "Use Python to read package.json, count the top-level keys, and return compact JSON only." Since the README says the cases "use stable JSON files" and shows this exact id, the divergence can mislead anyone diffing docs against disk or re-creating the case from the doc.
- [PTC_SCRIPTS_DIR is parsed but never used] `loadSettingsFromEnv` (src/utils.ts:89) populates `settings.scriptsDir` from `PTC_SCRIPTS_DIR`, but no code reads it (only src/contracts/settings.ts:19 and utils.ts reference the field), while `PythonSessionManager.toScript` hardcodes the default directory as `path.join(".pi", "scripts")` (src/python-session-manager.ts:1470). README's env-var section claims `PTC_SCRIPTS_DIR` sets "the legacy default directory for programmatic PythonSessionManager.toScript() exports" — it doesn't; setting it has no effect.
- [PTC_ALLOW_UNSANDBOXED_SUBPROCESS is mandatory but documented as optional; missing it hard-crashes every pi session] Verified in a clean env (fresh HOME, no PTC_* vars): after a successful `pi install`, the very next `pi` start (even `pi -p "hi"`) fails with `Error: Failed to load extension ".../src/index.ts": Failed to load extension: PTC runs Python as a local subprocess. Set PTC_ALLOW_UNSANDBOXED_SUBPROCESS=true to opt in.` and exits 1 — no tools, no session. Cause: `ptcExtension` awaits `createSandbox(settings)` unguarded (src/index.ts:1600) and `createSandbox` rejects when the flag is unset (src/sandbox-manager.ts:111-118); `loadSettingsFromEnv` defaults it to false (src/utils.ts:79). README (lines 280, 339-352) frames the var as an opt-in for "Execution mode" and never mentions it under Installation, so a fresh user's first run is a hard error. The extension should either default to allowing the subprocess (it is a local dev tool), degrade to a tool-level error, or the README must list the export as a required install step.
- [Initial pi_subagents clone failure is completely silent to the user] Verified in a clean env with an unreachable `PTC_SUBAGENTS_REPO_URL`: `ensureSubagentsEnv` returns `{status:"failed", reason:"git clone of the pi-subagents repo failed"}` (src/subagents-env.ts:412) but the caller is fire-and-forget and ignores the resolved result — `void ensureSubagentsEnv({ extensionRoot }).catch(...)` only handles throws (src/index.ts:1641-1645); the initial-clone failure path logs nothing (logWarning exists only for the managed-clone *update* path, src/subagents-env.ts:416). The venv is created, the session runs normally, and the user first learns of the failure when a cell dies with `ModuleNotFoundError: No module named 'pi_subagents'`. The failed status should be surfaced (session warning / footer / first `provision_kernel` notice).
- [ModuleNotFoundError recovery hint points at a package that does not exist on PyPI] When `import pi_subagents` fails in a cell, runtime.py:330 emits `help: install it with provision_dependency('pi_subagents') then re-run`. `pi-subagents` is not on PyPI (https://pypi.org/pypi/pi-subagents/json → 404) and provision_dependency installs from PyPI, so a model following the hint will hit a resolution failure and burn turns; the hint should suggest fixing the subagents sync (e.g. check ~/.cache/pi-ptc/subagents-sync.log / PTC_SUBAGENTS_REPO_URL) instead.
  - RESOLVED: the hint now maps known import-name/distribution mismatches (PIL->pillow, cv2->opencv-python, sklearn->scikit-learn, ...) before suggesting provision_dependency.
- [Sync stamp lands in different directories depending on how the extension is loaded] `getExtensionRoot()` (src/index.ts:265-269) returns `__dirname`, so when pi loads the manifest-declared `./src/index.ts` the stamp is written to `<pkg>/src/.ptc-subagents-sync.json`, while a `dist/index.js` load writes `<pkg>/.ptc-subagents-sync.json` — the path the git-tracked file and the subagents-env.ts header comment ("stamp lives inside this package's clone ... wiped by `pi update`") assume. Verified: clean-env pi -p run (src load) created `repo/src/.ptc-subagents-sync.json`; the tracked root-level stamp came from a dist load on the author's machine. Harmless for provisioning, but the tracked root stamp is not the one production pi actually reads/writes.
- [parseSectionedOutput does not recognize the new `tools:` section] `buildFinalOutput` (src/python-session-manager.ts:866) now appends a `tools:` section (per-tool call counts from the cell's nested-call ledger, emitted as `tools_text` on exec_done), but the section-marker regex in `parseSectionedOutput` (src/utils.ts:196) only matches `output|return|kernel|subagents` — and `OUTPUT_SECTION_NAMES` (src/utils.ts:152) omits `tools` too. In `renderCompletedOutput` (src/index.ts:186) the tools marker therefore fails to start a section: the `tools:` line and its indented body get appended (dedented) into the preceding `subagents` section's body instead of rendering as its own rule-separated block.
  - RESOLVED: `tools` added to OUTPUT_SECTION_NAMES and the section-marker regex.
- [normalizeToolResult fabricates bash exitCode 0] The bash branch of `normalizeToolResult` (src/tool-adapters.ts:231-238) returns `{ stdout: text, stderr: "", exitCode: 0 }` unconditionally, but pi's bash tool reports failures by appending `Command exited with code N` to the text output (node_modules/.../dist/core/tools/bash.js:203-204) and carries nothing in `details` — so a Python cell calling `bash("false")` sees `exitCode == 0` (the failure notice stays embedded in `stdout` instead). Any cell branching on `result["exitCode"]` or `result["stderr"]` gets wrong data; the adapter should parse the trailing exit-code line (or at least propagate the nonzero signal) rather than hardcode success.
